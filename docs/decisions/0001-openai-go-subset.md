# 0001: Port a subset of openai-go v3.98.0, with its Azure add-on

Status: Accepted (owner, 2026-11-09, through the lead). Drafted by Xo
Azure 1.

## Context

Azure OpenAI from Go is two modules: OpenAI's own client,
`github.com/openai/openai-go/v3`, sends the requests, and
`github.com/Azure/azure-sdk-for-go/sdk/ai/azopenai` adds Azure's
request and response types (On Your Data, content filter results). The
xo-lang/azure repo ports `azopenai` v0.9.0's types, but Xo has no
client to send them with, so Xo programs cannot call Azure OpenAI.

openai-go v3.98.0 is 232k Go lines, generated by Stainless, under the
Apache License 2.0 (Copyright 2026 OpenAI; no NOTICE file). The azure
repo is MIT, so the port gets its own repository.

## Decision

1. **Where.** A new repository, `github.com/xo-lang/openai`, licensed
   under the Apache License 2.0 (LICENSE is openai-go's text). Each
   ported file carries OpenAI's copyright and a note that it was
   changed from the original (Apache 2.0, section 4(b)); NOTICE.md
   names the source and version. Private until its first release and
   check-public pass, then public as xo-lang/aws and xo-lang/azure are.
2. **Pin.** openai-go v3.98.0. Later versions follow the azure repo's
   refresh process (vectors re-run against the new release, drift
   recorded).
3. **First slice.**
   - The client and its options (`option`): base URL, API key and
     organization and project headers, extra headers and query values,
     max retries, request timeout, middleware; Go's retry rules
     (`x-should-retry`, `retry-after-ms`, `retry-after`, 408, 409, 429
     and 5xx, its backoff), its `User-Agent` and `X-Stainless-*` headers,
     and its error type (status, request, the API's `error` object).
   - Chat completions: create, the streamed form (server-sent events,
     ending at `[DONE]`), and Go's stream accumulator for content and
     tool calls. Stored completions (list, retrieve, update, delete,
     messages) only if they come cheap in the same slice.
   - Embeddings: create, with Go's base64 float decoding.
   - The models these need (`shared` and `shared/constant` parts), as
     Xo structs and enums; Go's `param.Opt` and omitted-versus-null
     fields as Xo options, written to the JSON Go writes.
   - The Azure add-on, as Go's `azure` package: `with_endpoint(endpoint,
     api_version)` (the `/openai/deployments/<model>/...` path rewrite
     and `api-version` query), `with_api_key` (the `Api-Key` header),
     `with_token_credential` (azcore's bearer token policy, default
     scope `https://cognitiveservices.azure.com/.default`), and
     `with_unsafe_allow_http`.
4. **Dependencies.** Go's `azure` package imports azcore (the
   TokenCredential, the bearer token policy and the pipeline), not
   azidentity. So `xo-lang/openai`'s `azure` package requires the
   azure repo's root module (`github.com/xo-lang/azure`, which holds
   azcore), and the caller passes any credential (azidentity's
   included). `xo-lang/azure/ai/azopenai` (its own module) then
   requires `xo-lang/openai`. The module graph has no cycle, so the
   add-on stays where Go puts it.
5. **Streaming** goes through azcore's server-sent events reader (the
   azure repo's port of azcore v1.24.0 `streaming/sse.go`), if its
   behavior matches openai-go's `packages/ssestream` on the vectors;
   where they differ, openai-go's rules win and the port has its own
   reader.
6. **Vectors.** A Go program runs openai-go v3.98.0 against a local
   fake server (loopback only) and prints every request (method, URL,
   headers with volatile values masked, body) and every result or
   error; Xo replays the same calls against the same fake. Never a
   real OpenAI or Azure endpoint, and no real key.

## Amendment 1 (2026-11-09): streaming has its own reader

Point 5 is settled the other way: the root module reads server-sent
events itself (`stream.xo`, a port of openai-go's `packages/ssestream`),
so it does not require the azure repository; only the `azure` package
does. openai-go's rules differ from azcore's reader in what matters
here: any event whose JSON has an `error` field ends the stream with
`received error while streaming`, `[DONE]` is matched as a prefix of
the data, an event not ended by a blank line is dropped, and a line may
be 32 MiB.

## Amendment 2 (2026-11-10): the Responses API

Go's azopenai v0.9.0 examples call `Responses.New` seven times and
`NewStreaming` and `Delete` once each, so the Responses API moves out of
Deferred, as the subset those calls use (`responses.xo`):

- `response` (POST responses), `response_stream` (the same with
  `"stream": true`, through the root module's event reader) and
  `delete_response` (DELETE responses/<id>, `Accept: */*`, the id
  escaped as Go's FormatPath; an empty id is Go's `missing required
  response_id parameter` before any request).
- Parameters: the scalar options, include, metadata, service tier,
  truncation, input as text or items (an input message with text and
  image parts, a text message, a function call's output), reasoning
  (effort, summary), tool choice (a mode or a function) and function
  tools; anything else through `extra`. The body keeps Go's struct
  order.
- Results: the response with its output items (message parts with
  annotations, function calls, reasoning summaries), usage with cached
  and reasoning tokens, the error, `output_text()` as Go's OutputText,
  and `raw` for the rest; stream events with their common fields and
  `raw`. An `error` event is an ordinary event, as in Go (its JSON has
  no top level `error` field); a `response.failed` event carries the
  response's error.
- The `azure` package routes `responses` to `/openai/responses`, not
  the deployment path, as Go does.

Still deferred from the Responses API: retrieve, cancel, input items,
input tokens, compaction, the accumulator and the websocket transport,
built in tools (file and web search, computer use, MCP, code
interpreter) and structured output helpers. Vectors: sections p1 to
p8 and z6 of the Go program.

## Amendment 3 (2026-11-10): images

Go's azopenai examples call `Images.Generate` once; `Edit` comes in the
same slice because it is the first multipart route and audio needs the
same encoder (`form.xo`).

- `generate_images` (POST images/generations, JSON in Go's struct order)
  and `edit_images` (POST images/edits, a multipart form). The form is
  written by std/multipart (`write`, `random_boundary`, Go's 60 hex
  digit boundary): fields sorted by name as Go's apiform writes them,
  one image as `image`, several as `image[]` each, a file's name and
  content type defaulting to Go's `anonymous_file` and
  `application/octet-stream`.
- The `azure` package routes images/edits (and the audio
  transcriptions and translations routes) by the form's `model` part,
  as Go's getMultipartRoute; without one, Go's `unable to find the model
  part in multipart body`.
- Deferred: variations, streamed generation and edits, the GIF and SVG
  options. Vectors: i1 to i5 and z7 (the boundary masked on both sides).

## Amendment 4 (2026-11-10): audio

Go's azopenai examples call `Audio.Transcriptions.New`,
`Audio.Translations.New` and `Audio.Speech.New` once each.

- `transcribe` (POST audio/transcriptions) and `translate` (POST
  audio/translations) as multipart forms through `form.xo`: a list
  field is `name[]` for each value (`include[]`,
  `timestamp_granularities[]`), a float is Go's FormatFloat 'f' -1
  (`to_fixed(-1)`). The result of `transcribe` holds Go's response
  union's fields (text, language, duration, segments, the tokens or
  duration usage) with `raw`; `translate` gives the text.
- `speech` (POST audio/speech, JSON, `Accept:
  application/octet-stream`) gives the status, content type and bytes,
  as Go's *http.Response.
- The `azure` package routes all three by model: the form's `model`
  part for transcriptions and translations, the JSON `model` for
  speech.
- Deferred: streamed transcriptions, the text, srt and vtt formats (Go
  points those at Client.Post), chunking strategy, known speakers,
  custom voices and voice consents. Vectors: a1 to a5 and z8.

## Amendment 5 (2026-11-10): legacy completions

Go's azopenai examples call `Completions.New` and `NewStreaming` once
each. `completion` and `completion_stream` (POST completions, the second
with `"stream": true` through the root module's event reader) take a
prompt as text, texts, tokens or token lists, Go's scalar options,
`logit_bias` (sorted keys, as Go's map) and `stop` (chat's Stop); the
result is Go's Completion with its choices and usage, logprobs left in
`raw`. The `azure` package already routes `/completions` by model.
Vectors: l1 to l3 and z9. With this, every client call in Go azopenai
v0.9.0's examples has a port.

## Deferred

The rest of the Responses API (Amendment 2), assistants, threads and the other
beta APIs, streamed audio and custom voices, image variations and streaming, files and uploads, batches, fine tuning,
vector stores, moderation, models, containers, the admin APIs,
realtime and websockets, webhooks, the Bedrock and other provider
packages, and `azopenai`'s re-ported helpers that need the client.
Each is its own later slice, by user need.

## Consequences

- One more public repository to check before each push
  (check-public, gitleaks).
- The azure repo gets a pointer decision naming this one, and
  `ai/azopenai`'s README stops saying the client is missing once the
  first slice is released.
